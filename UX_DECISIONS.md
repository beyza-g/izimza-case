# UX / Architecture Decision Catalog

This is the detailed companion to [README.md](./README.md)'s problem→solution
table: every UI/UX and architectural call made while building this case
study, grouped by concern, with the concrete reasoning behind each one — not
the "what" (the code already shows that), the "why."

## Forms & Data Entry

| Decision | Problem It Solves | User/Evaluator Benefit |
| --- | --- | --- |
| A red `*` was added next to required field labels (`ProfileView.vue`), and the Zod schema marks the same fields as required (`f.required ? z.string().min(1, ...) : z.string()`) | Which fields were required stayed ambiguous until the user hit submit | Expectations are clear before the form is even filled in; since the visual marker and the schema both derive from the same `fields` config, they can never drift apart |
| The Save/Cancel buttons are disabled based on `vee-validate`'s `meta.dirty` state (`:disabled="!meta.dirty"`, on both the Profile form and the Save button) | Being able to hit "Save" on a form with zero changes meant a pointless PATCH request and a meaningless "saved" confirmation | The button state reflects the form's actual state — the user can't accidentally trigger an empty save; the UI answers "did anything change?" on its own |
| A dedicated phone mask (`src/lib/phone.ts`): `0(5XX) XXX-XXXX` format, with `extractDigits`/`formatPhone` defined in exactly one place, and both the input mask and the Zod regex (`PHONE_REGEX`) checking against that same shape | A free-text phone field is open to formatting errors, and letting the mask and the validation schema evolve independently invites them silently drifting out of sync | The user sees the correct format as they type, so an invalid format can never actually be entered; `maskPhone` reveals only part of the number on the OTP screen (`0(551) •••-6158`) — security and consistency come from the same module |
| KVKK (Turkish data-protection) consent is not re-requested as a checkbox on the Profile page — only a passive notice ("saving your profile means you accept...") plus a "Read the notice" link (`profile.kvkkText`) | The user already accepted the KVKK notice at signup; re-confirming it via a checkbox on every single profile update would be unnecessary friction and a requirement the real app itself doesn't impose | The save flow stays uninterrupted; the legal disclosure stays accessible (the link is right there) without turning into a repeated consent gate that wears the user down |
| In the change-password modal (`ChangePasswordModal.vue`), the rules (8+ characters, upper/lowercase, digit, match) aren't a static list — they're a checklist that turns green live as the user types | A static rule list doesn't tell the user which rule they haven't met yet in the moment — they'd only find out via an error message after submitting | Instant feedback — the user sees exactly which rule is still unmet before they ever submit, removing the trial-and-error loop entirely |

## Accessibility

| Decision | Problem It Solves | User/Evaluator Benefit |
| --- | --- | --- |
| `ChangePasswordModal` auto-focuses the current-password field on open (`currentPasswordInput.value?.focus()`) | On open, focus stayed elsewhere on the page (or nowhere), forcing a keyboard/screen-reader user to take an extra step just to find the form | A keyboard user can start typing the instant the modal opens; a screen reader clearly announces where focus landed |
| `AlertDialog`/`DropdownMenu` components use reka-ui's `DismissableLayer`/`FocusScope` primitives, which provide Escape, focus-trapping, and outside-click dismissal for free; the OTP bottom sheet and the sidebar's user-card popover additionally got `role="dialog"`/`aria-modal="true"` and an explicit Escape listener (the user-card popover previously only closed on outside-click/scroll, with no Escape handling) | Some overlays (the ones not built on reka-ui) offered keyboard users no way to dismiss them with Escape — a mouse-dependent close mechanism | Every overlay can now be dismissed consistently via the keyboard; this is the concrete output of this project's accessibility consistency audit |
| Each of the 6 OTP digit inputs got an `aria-label="Digit {n}"` (`timestamp.otp.digitLabel`) | A screen reader read a run of 6 identical inputs as generic "text box, text box, text box..." with no way to tell them apart | A screen-reader user hears exactly which digit position they're on, so they can enter the code in the right order with confidence |
| The toast notification container got `role="status"` + `aria-live="polite"` (`ToastHost.vue`) | When a toast appeared (e.g. "Document deleted", "Saved"), a screen-reader user had no way of knowing — the notification was purely visual | The screen reader announces the toast text automatically, without interrupting the rest of the page ("polite"); a visually-impaired user learns the outcome of their action too |

**Known, scoped gap**: hand-rolled overlays like `ChangePasswordModal` and the user-card popover don't use a dedicated focus-trap library — `Tab` can still escape to the page behind them. This is a deliberately scoped-out gap, not a full WCAG audit.

## Feedback & State

| Decision | Problem It Solves | User/Evaluator Benefit |
| --- | --- | --- |
| One centralized toast system (`ToastHost.vue` + `pushToast`) and a three-way error taxonomy in the axios interceptor: a cancelled request (`axios.isCancel` → silently ignored, no toast), a network error (never reached a server → generic "connection error" toast), a 4xx (field-level, shown via the form's own error message, no toast), and a 5xx (generic "server error" toast) | If every call site decided on its own how to show its own error, the result would be an inconsistent voice and a risk of multiple notifications for the same failure; also, showing a request the user themselves cancelled as an "error" would send the wrong signal | The user is always informed from the same place, in the same voice; a genuine failure never gets conflated with the user's own action (a cancellation, a form validation error) |
| Loading states use `SkeletonBlock.vue` instead of an empty space or a spinner — a shimmer-animated placeholder sized to match the space its content will eventually occupy (`StatCard.vue`, the dashboard's stat row) | Leaving blank space until data arrives, or having content pop in abruptly and shift the layout (CLS), is a problem observed on the real portal.izimza.com too | The layout stays stable while the page loads, with no "jump" once data arrives; the user can visually tell something is loading |
| The timestamping mutation uses optimistic update + rollback (`useTimestampMutation.ts`'s `onMutate` updates the credit/document data immediately; `onError` rolls it back via `previousAccount`/`previousDocuments`) | Waiting for the server response made the action feel like nothing was happening; but leaving the optimistic update unhandled on failure would mean showing the wrong balance after a failed request | The user sees the credit/status change the instant they act (feels fast), and on failure the data silently and correctly reverts — they never see an incorrect balance |
| Disabled buttons clearly state why they're disabled — e.g. on insufficient credit, the panel shows `insufficientTitle`/`insufficientDescription` with "{queued} documents need {cost} credits, your balance is {remaining}" instead of just graying the button out | A gray button alone doesn't explain "why can't I click this," forcing the user to guess | The user immediately sees exactly what they need to do to complete the action (upgrade credits), with no support-ticket-worthy confusion |
| The OTP step's status row (below the digit boxes — countdown, or the code-validity value once wrong/expired) is a fixed-height row in every state (`CommitModalContent.vue`) | A variable-height row shifted the primary button up/down whenever an error appeared, risking a mis-tap right after a failed attempt | The button sits in the same place through every state change — reacting quickly to a wrong-code or expiry message never lands the next tap on the wrong control |
| The OTP step has exactly one primary call-to-action that relabels itself by state (`Doğrula` → `Tekrar dene` on a wrong code → `Yeni kod gönder` once expired) instead of a separate always-visible resend link alongside it | A second, always-present resend control competed with the primary button for attention and duplicated the same underlying action, leaving two ways to do overlapping things | One clear next action at a time — no ambiguity about which control actually resends versus verifies, and expiry's only way forward is unmistakable |
| A disabled primary button anywhere in this step uses a flat muted background/text (`bg-muted`/`text-muted-foreground`), never a faded/translucent version of the active accent color | A translucent-but-still-colored disabled button reads as "maybe still clickable," inviting a wasted tap | Disabled unmistakably looks disabled in every state the button passes through (incomplete code, mid-submit, post-error) |

## Responsive & Navigation

| Decision | Problem It Solves | User/Evaluator Benefit |
| --- | --- | --- |
| A three-tier sidebar: a fixed 248px labeled menu on desktop (`lg:`), a 76px icon rail on tablet (`md:`), and fully hidden on mobile — replaced there by a bottom tab bar (`AppBottomNav.vue`) | A single fixed-width sidebar is either wasted space on desktop or unusable on tablet/mobile | Navigation looks right for every breakpoint — space-efficient on tablet, thumb-reachable on mobile, fully labeled and clear on desktop |
| The tablet rail (between `md:` and `lg:`) expands from 76px to 248px on `@mouseenter`/`@mouseleave` (the `expanded` ref in `AppSidebar.vue`) | A fixed icon-only rail hides the labels, forcing the user to memorize which icon goes where | Labels appear on hover, so the tablet user can see the full menu without an extra click; the expansion is temporary, so no permanent space is lost |
| The timestamping flow's right-hand panel renders as a side panel on desktop and as a fixed bottom sheet on mobile (`fixed inset-0`, same markup, driven purely by responsive classes) — not two separate components, one piece of content in two different layouts | Maintaining two separate components (a desktop panel + a mobile modal) would mean keeping one state machine in sync across two places, an easy thing to let drift apart | One state machine, one single source of correct behavior — a side-panel feel on desktop, a native-feeling bottom sheet on mobile, but the underlying logic is never forked in two |
| Long file/document names truncate to one line (CSS `truncate`) with a native `title` attribute carrying the full name, applied consistently across every document listing: the Timestamp queue (`TimestampView.vue`), Dashboard's recent-documents table (`DashboardView.vue`), and the file preview sheet's header (`FilePreviewSheet.vue`) | A long file name either wrapped and broke the row's layout, or was cut off with no way to recover the full name at a glance | Rows stay a single, predictable height regardless of name length; hovering any truncated name reveals the full one via the browser's own tooltip, with no extra JS or custom tooltip component needed |

## Architecture

| Decision | Problem It Solves | User/Evaluator Benefit |
| --- | --- | --- |
| Single-source-of-truth principle: the `wallet.ts` Pinia store was removed, and the credit balance is now read exclusively through `useAccount()` (the TanStack Query cache); Pinia is reserved for genuinely client-only state (auth, theme) | The credit balance used to live in both a Pinia store and the account query response separately — one could update after a mutation while the other went stale | The balance is the same everywhere, read from one source — the "which number is correct" ambiguity disappears; anyone reading the codebase knows exactly where to look for server data versus client data |
| Splitting `TimestampView.vue`'s 4-state (idle→ready→otp→result→send) flow into `useDocumentQueue()`/`useOtpFlow()` composables was deliberately deferred — noted in the README, not done | Splitting early risks drawing the wrong abstraction boundaries before all the flow's edge cases have actually settled | Rather than splitting before the right boundaries are clear, the current single-file flow is left working and tested for a future refactor — avoiding the risk of premature abstraction |
| TanStack Query cache strategy: every query defines a `staleTime` and `retry: false` — no automatic refetch on every navigation, and TanStack's own retry mechanism doesn't race against axios's retry-toast | Firing a network request on every navigation was both a performance cost and an anti-pattern observed in the real app; also, TanStack retry plus axios's retry-toast running simultaneously sent the user multiple notifications for the same failure | Navigation feels instant/served from cache, with no wasted network traffic; when a request does fail, the user sees exactly one clear error notification |
| Every HTTP request passes through a single axios interceptor layer (`unwrapResponse`, the error taxonomy, 401→token refresh, cancellation signaling) | If response-unwrapping and error handling were written separately at every call site, one getting updated while another was forgotten would make inconsistency inevitable | Adding a new API call never requires rewriting error/unwrap logic — the behavior is automatically consistent; anyone reviewing the codebase can read error handling in one place and understand it for the whole app |
| The design token system stays OKLCH-based CSS custom properties (`--background`, `--primary`, etc., as full `oklch(...)` function strings), with the Tailwind config referencing them directly; `shadcn-vue` was integrated into the project later, scoped only to the dropdown-menu/alert-dialog components (hand-porting the CLI's generated Tailwind v4-only classes to v3) | Never having run `shadcn-vue init` from the start left a gap between the stated stack (Tailwind + Shadcn Vue) and the actual app; running the CLI directly, meanwhile, silently produced non-working CSS due to v4-only syntax | Design tokens come from one consistent source (OKLCH custom properties); shadcn-vue components can be added where needed without breaking the existing hand-built components, integrated in a v3-compatible way — closing the gap between the stated stack and the actual code |
| An `AbortController` is threaded through `TimestampView.vue`'s file-upload loop and its OTP-verify/commit loop, all the way into `useTimestampMutation`'s `mutationFn`, and aborted on `onBeforeUnmount`. **Scope note**: this is deliberately narrow — it only covers this one flow. `useAccount`/`useDocuments`/`useProfile`/`useSecurity` and every other TanStack `useQuery` do not accept or forward a cancellation signal, so there is no app-wide "every pending request is cancelled on every navigation" mechanism | Navigating away from `/timestamp` mid-flow left upload/verify requests running to completion in the background with no way to stop them, and a stray `setTimeout` wasn't cleared on unmount either | Leaving the one credit-consuming, irreversible flow cleanly cancellable was worth the wiring; the axios interceptor treats a cancellation (`axios.isCancel`) as a silent reject rather than a network-error toast, so leaving mid-flow never surfaces a false "something went wrong" |
| Countdown-timer, OTP-digit-input, and recipient-selection logic (previously inline in `TimestampView.vue`/`CommitModalContent.vue`), phone-input caret handling (previously inline in `ProfileView.vue`), and several pure helpers (`formatBytes`/`inferDocType`, the archive-usage % calc, orphaned-error cleanup) were extracted into `src/composables/` and `src/lib/` respectively; the password-rule regexes now live in one place (`src/lib/passwordRules.ts`) that both the Zod schema and the live checklist import | Inline component logic couldn't be tested or read in isolation, and the password-rule regexes specifically were duplicated verbatim between the Zod schema and the UI checklist — two copies that could silently drift apart | Behavior and render output are unchanged (verified via type-check/lint/build plus a manual pass through every affected flow); the logic is now independently readable, and the password-rule duplication — a real correctness risk, not just a style nit — is closed at the source |
| Dashboard's delete confirmation, Timestamp's clear-queue confirmation, and Timestamp's leave-page confirmation were three near-identical hand-rolled `AlertDialog` blocks, consolidated into one shared `ConfirmDialog.vue` wrapper | The same confirm/cancel markup was copy-pasted three times, so a visual tweak to one had to be manually repeated in the other two — an easy thing to forget and let drift | The duplication closes at one source; each site's own confirm logic (Dashboard's race-safe delete guard, the leave-confirmation's Promise-based flow) was left completely untouched — only the markup moved |
